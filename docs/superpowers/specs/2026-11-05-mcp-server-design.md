# MCP-сервер инструментов 1С для ИИ-ассистента (`objects`)

Статус: проект на утверждение. Источник требований — ТЗ от 2026-11-05.
Решения, которых нет в ТЗ, собраны в разделе «Решения вне ТЗ» и отмечены как
предложения автора; утверждаются вместе со спецификацией.

## Назначение и границы

Локальный MCP-сервер открывает ассистенту инструменты работы с базой 1С через
существующий HTTP-сервис объектов (расширение `СчетаМагазина`, корень
публикации `objects`). Сервер работает только через сервис объектов: в
информационную базу напрямую не ходит, метаданные не читает. Основная
конфигурация, расширение и сервис объектов не меняются.

Пользователи: менеджер — пишет просьбы словами в чат; ассистент — выбирает
инструмент по его описанию и формирует вызовы.

Сценарии:

1. Менеджер спрашивает, какие в базе есть документы про счета; ассистент
   находит типы.
2. Ассистент узнает поля типа: типы значений, обязательность, где искать
   значение ссылкой.
3. Ассистент находит покупателя, организацию и товар по части наименования.
4. Ассистент читает объект по идентификатору.
5. Менеджер просит словами выставить счет; ассистент создает непроведенный
   счет и называет его номер.
6. Если 1С отклоняет запись, ассистент получает текст отказа и исправляет
   вызов или спрашивает менеджера.

Сервер локальный: его запускает клиент ассистента (stdio-процесс), сетевой
доступ к самому серверу не предусмотрен.

Вне рамок: изменение, удаление и проведение объектов; доработка сервиса
объектов и расширения; удаленный доступ к серверу по сети.

## Анти-цели (что сделало бы результат неудачным даже при работающем коде)

- Сервер дублирует правила сервиса объектов: проверяет обязательность, форматы
  или права сам. Единственный арбитр — сервис и штатная проверка 1С.
- Сервер подставляет значения за пользователя: проставляет дату текущей,
  молча выбирает первый результат поиска, дозаполняет шапку.
- Сервер кэширует описания типов или объекты: устаревшая схема опаснее
  лишнего запроса.
- Учётные данные попадают в сообщения об ошибках, журналы или описание
  инструментов.
- У ассистента появляется способ изменить базу помимо одного изменяющего
  инструмента.

## Рассмотренные подходы

1. **Тонкая обертка 1:1** — пять инструментов, зеркально пяти маршрутам
   сервиса объектов. Контракт сервиса изначально спроектирован под
   ИИ-ассистентов (сценарий «найти тип → узнать поля → подобрать ссылки →
   создать»), каждая переупаковка — новая точка расхождения с ним.
   **Выбран.**
2. **Сценарные укрупненные инструменты** («подобрать ссылки и создать счет
   одним вызовом»). Отклонен: модель теряет пошаговый контроль, подтверждение
   перед изменяющим действием размывается, отказ 1С труднее привязать к шагу.
3. **Динамическая генерация инструментов из `/types`** (инструмент на тип).
   Отклонен: сотни инструментов перегружают контекст клиента; списки
   инструментов у клиентов обновляются не мгновенно.

## Решения вне ТЗ (предложения автора — утвердить)

1. **Стек:** Node.js 22 (установлен, 22.23.4) + TypeScript + официальный
   `@modelcontextprotocol/sdk`, транспорт stdio; HTTP-клиент — встроенный
   `fetch`; единственная внешняя зависимость — SDK; сборка в один JS-файл.
   Python отпадает: установлен 3.9.7, официальному SDK нужен 3.10+.
2. **Папка:** `mcp-server/` в корне репозитория. Это не доработка 1С —
   в `extensions/` ему не место; рядом `docs/` и `build/`.
3. **Клиент приемки:** ZCode, новый чат в этом проекте; сервер подключается
   проектной конфигурацией MCP без секретов (только команда и аргументы).
4. **Конфигурация:** переменные окружения `OBJECTS_URL` и `OBJECTS_AUTH`;
   если не заданы, сервер сам читает `src/tests/.env` — тот же стенд и тот же
   единственный источник учетных данных, что у `objects.http`. Не найдено ни
   то ни другое — внятная ошибка при старте.
5. **Имена инструментов** — snake_case ASCII (ограничение MCP); **описания
   инструментов** — на русском: чат русскоязычный.
6. **Признак «изменяющего»** — двойной: MCP-аннотация `readOnlyHint=false`
   у `create_object` плюс явная пометка в тексте описания («создает объект
   в базе»). Клиенты показывают аннотации по-разному; текст доходит всегда.
7. **Ответы инструментов** — JSON текстом в content; модель читает структуру
   без потерь, больших преобразований не требуется.
8. **Таймаут HTTP-запроса к сервису** — 30 секунд; истечение трактуется как
   недоступность сервиса.

## Инструменты

Имя сервера при подключении — `objects` (как корень публикации сервиса);
у клиента инструменты видны как `objects_*`. Пять инструментов, зеркально
маршрутам:

| Инструмент | Назначение | Изменяющий | Параметры |
| --- | --- | --- | --- |
| `find_types` | Найти типы (справочники и документы) по подстроке имени или представления; без запроса — все | нет | `q?` |
| `describe_type` | Описать тип: поля (типы значений, обязательность, записываемость, причина недоступности), табличные части, ссылки с типом для поиска, значения перечислений, правила | нет | `name` |
| `find_objects` | Найти объекты типа по подстроке наименования (справочники) или номера (документы); способ подобрать ссылку для поля; ответ включает `hasMore` | нет | `type`, `q`, `limit?` |
| `read_object` | Прочитать объект по UUID: шапка, табличные части, код/номер, дата, признак проведения | нет | `type`, `id` |
| `create_object` | Создать объект (справочник или непроведенный документ) по схеме `describe_type`; ответ — id, код/номер, дата | **да** | `type`, `header`, `tables` |

Требования к описаниям: каждое описание называет действие, результат и когда
инструмент вызывать; у `create_object` описание прямо говорит, что инструмент
создает объект в базе и требует подтверждения менеджера. `id` объектов —
UUID строкой в нижнем регистре (сервис принимает только нижний).

## Ошибки и недоступность

Ошибки инструментов возвращаются результатом с `isError=true`, а не ошибками
протокола: модель должна прочитать текст и отреагировать, а не получить
исключение клиента.

- **Отказ 1С** (любой HTTP-ответ сервиса с ошибкой: `400/403/404/415/422/500`,
  коды `unknown_type`, `invalid_request`, `forbidden`, `creation_not_allowed`,
  `not_found`, `validation_failed`, `unsupported_media_type`, `internal_error`):
  текст вида «1С отклонила операцию (validation_failed): Объект не прошел
  проверку заполнения», за ним — `details` с `path` и сообщениями; ассистент
  исправляет вызов или спрашивает менеджера.
- **Недоступность сервиса** (не удалось соединиться, таймаут, разрыв связи,
  отказ публикации платформой до сервиса): текст вида «Сервис объектов
  недоступен: <причина>». Формулировка отличима от отказа 1С: ассистент
  сообщает менеджеру, а не правит вызов.
- **Доступ запрещен публикацией** (401/403 от платформы): отдельный текст
  «Доступ запрещен: проверьте учетные данные сервиса».
- Учётные данные и заголовки в сообщениях об ошибках не раскрываются.

## Конфигурация и запуск

- `OBJECTS_URL` — базовый адрес до маршрута (как в `objects.http`:
  `${OBJECTS_URL}/types`, `/type`, `/search`, `/object`); `OBJECTS_AUTH` —
  готовое значение заголовка `Authorization`.
- Порядок чтения: переменные окружения процесса; иначе файл `src/tests/.env`
  (простые строки `KEY=VALUE`), путь разрешается от расположения сервера.
- Запуск: `node mcp-server/build/index.js` из корня проекта; подключение —
  проектная конфигурация MCP клиента ZCode (без секретов: команда и
  аргументы; учетные данные сервер берет из `.env`).

## Приемка

1. Новый чат ZCode в этом проекте видит пять инструментов сервера.
2. Контрольный пример: просьба словами «выставь счет на оплату покупателю
   <имя> на <товар>» — ассистент находит тип, узнает поля, подбирает
   покупателя, организацию и товар поиском, создает счет и называет его
   номер; документ в 1С непроведен (проверяет пользователь).
3. Перед `create_object` клиент запросил подтверждение (изменяющий
   инструмент).
4. Отказ: вызов с пропущенным обязательным полем — ассистент получил текст
   отказа 1С и исправил вызов или спросил менеджера.
5. Недоступность: при недоступном сервисе ассистент получает сообщение
   «сервис недоступен», отличимое от отказа 1С.

## Тестовые данные

Решение пользователя от 2026-11-05: создающие запросы к живому сервису при
разработке разрешены — в план входит автоматическая E2E-проверка изменяющего
пути (`create_object`) и отказов штатной проверки на живом стенде. Созданные
объекты остаются в базе (сервис объектов не умеет удалять); объем — минимально
достаточный для покрытия изменяющего пути и отказов, по правилу спеки сервиса
«тестовые данные не создаются без согласования» согласование получено этой
записью. Read-only проверки (types, type, search, object) выполняются без
создания объектов на существующих демо-данных.
