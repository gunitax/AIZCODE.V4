# Универсальный HTTP-сервис объектов 1С (`objects`)

Статус: утверждена пользователем в текущей сессии. Источник требований — ТЗ
от 2026-11-04. Решения пользователя: БСП-обслуживаемые табличные части исключены
из записи; создание ограничено объектами `_Демо*` и явным списком допуска
(`Валюты`), список — на развитие. Заменяет спецификацию
[2026-10-25-shop-invoices-design.md](2026-10-25-shop-invoices-design.md): контракт
счетов выводится из эксплуатации, счёт создаётся через общий маршрут создания.

## Назначение и границы

Один сервис описывает, ищет, читает и создаёт объекты 1С поддерживаемых видов.
Аудитория — разработчики внешних систем и их ИИ-ассистенты: `/types` и `/type`
дают столько, что запрос собирается без документации по конфигурации. Сценарии:
найти тип по слову, узнать поля и обязательность, найти объекты по наименованию
или номеру, прочитать объект по UUID, создать справочник или непроведённый документ.

Основная конфигурация не меняется. Доработка — в существующем расширении
`СчетаМагазина` (`src/extensions/СчетаМагазина/`), HTTP-сервис `СчетаМагазина`
с корнем `objects`. Имена общих модулей (`СчетаМагазинаМетаданные`,
`СчетаМагазинаДанные`) сохраняются как исторические: переименование меняет
состав расширения без пользы для контракта.

Вне рамок: изменение и удаление объектов, проведение документов, регистры,
константы, отчёты, обработки и прочие виды метаданных, дополнительные реквизиты
и сведения БСП, общие реквизиты конфигурации.

Анти-цели (что сделало бы результат неудачным даже при работающем коде):
подмена штатной проверки заполнения своей схемой обязательности; молчаливое
обрезание строк, округление чисел, преобразование строк в числа или даты;
подстановка значений за пользователя; раскрытие факта существования недоступных
объектов; трактовка повтора создания после потери ответа как безопасной.

## Рассмотренные подходы

1. **Обобщить существующие модули.** Модули уже описывают документ по метаданным
   и преобразуют значения по схеме; привязка к счёту локализована в нескольких
   точках. Схема становится параметрической по `Вид.Имя`, правила прежнего
   сервиса переносятся на все типы. **Выбран.**
2. **Новый сервис на каждый вид объектов.** Отклонён ТЗ: логика одна и та же,
   стоимость неоправданна.
3. **Переписать обобщённый слой с нуля.** Отклонён: существующий слой уже
   проходит приёмку на счётах, переписывание ломает проверенную логику.

## Маршруты

Маршруты фиксированы ТЗ; других операций сервис не предоставляет.

| Сценарий | Запрос | Успех |
| --- | --- | --- |
| Найти типы | `GET …/types?q=<слово>` | `200` |
| Описать тип | `GET …/type?name=<Вид.Имя>` | `200` |
| Найти объекты | `GET …/search?type=<Вид.Имя>&q=<строка>&limit=<n>` | `200` |
| Прочитать объект | `GET …/object?type=<Вид.Имя>&id=<uuid>` | `200` |
| Создать объект | `POST …/object` | `201` |

Имя типа — как в метаданных: `Справочник._ДемоПартнеры`,
`Документ._ДемоСчетНаОплатуПокупателю`. Поддерживаемые виды: `Справочник`,
`Документ`. Доступ — обычная аутентификация HTTP-сервисов базы учётной записью
1С, с её правами; привилегированный режим не включается. Сессии сервиса —
`AutoUse`, как заведено.

Тела и ответы — JSON в UTF-8; у ответов `Content-Type: application/json;
charset=utf-8` без BOM. Создание принимает `application/json` (допустим
`charset=utf-8`), иначе `415`.

## Поддерживаемые виды и типы значений

Значения полей, читаемые и записываемые: строка, число, дата, булево, ссылка
на справочник или на документ, значение перечисления. Типовое описание поля
помечает всё остальное (составные, хранилище значений, УИД, `Время`) как
недоступное: в `/type` — `writable=false` с `reason`, при записи — отказ `400`,
при чтении поле опускается без сбоя. Если среди типов поля есть хоть один
неподдерживаемый, поле целиком недоступно для записи (правило прежнего сервиса).

Поля с несколькими поддерживаемыми типами передаются типизированным значением
`{"type": "<имя из описания>", "value": …}`; одиночный тип — значением напрямую.

| Тип | Запись | Чтение |
| --- | --- | --- |
| Строка | строка JSON; проверка длины, фиксированная длина | строка |
| Число | число JSON; проверка разрядности, точности, знака | число |
| Булево | `true`/`false` | `true`/`false` |
| Дата | строка ISO 8601 без зоны; часть «Дата» — `YYYY-MM-DD`, иначе `YYYY-MM-DDTHH:mm:ss`; смещения и `Z` отклоняются | в том же виде |
| Ссылка на справочник | строка UUID существующего доступного элемента, не помеченного на удаление, не группы | UUID строкой; пустое — `null` |
| Ссылка на документ | строка UUID существующего доступного документа, не помеченного на удаление | UUID строкой; пустое — `null` |
| Перечисление | техническое имя значения строкой | имя строкой; пустое — `null` |

`null` — штатное пустое значение поля; обязательность проверяет 1С. Ссылка,
указывающая на несуществующий, недоступный или помеченный объект, даёт одну и
ту же ошибку без раскрытия, что именно не так.

## Описание типов

`GET /types` перечисляет справочники и документы конфигурации: ответ
`{"types":[{"name":"Справочник._ДемоПартнеры","kind":"catalog","title":"Партнёры","creatable":true}]}`,
сортировка по имени; `kind` — `catalog` или `document`; `creatable` — признак
разрешения на создание (см. «Разрешение на создание»). Необязательный `q` —
подстрока (без учёта регистра) в имени или синониме вида; пустой или
отсутствующий — все виды. Выдача не разбивается на страницы: видов в базе
порядка сотни, полный список занимает единицы КБ; это записано здесь как
сознательное ограничение.

`GET /type?name=` описывает один вид: `{"type", "kind", "title", "creatable",
"fields", "tables", "rules"}`. `fields` — стандартные реквизиты и реквизиты;
`tables` — табличные части с их `fields`. Для поля: `name`, `title`, `writable`,
`required`, `types[]`, при недоступности — `reason`. Для типа значения:
квалификаторы строки и числа, части даты; ссылке — `catalog`/`document` и
`searchUrl` (`/search?type=…`); перечислению — `enumeration` и `values` с
техническими именами и представлениями; неподдерживаемому — исходное имя.

Табличные части, обслуживаемые механизмами БСП, исключены из записи закрытым
списком имён — `ДополнительныеРеквизиты`, `КонтактнаяИнформация`: в `/type`
они описаны с `writable=false` и причиной, запись такой части отклоняется
понятной ошибкой. Сырая запись в них портит хранимые БСП структуры (например,
JSON значений контактной информации), и штатная проверка заполнения этого
не замечает. Список расширяется при обнаружении новых обслуживаемых частей.

## Разрешение на создание

Чтение, поиск и описание доступны по всему читаемому пользователю. Создание
ограничено правилом сервиса: объекты, чьё имя начинается с `_Демо`, плюс явный
список допуска — на текущий момент справочник `Валюты`. Список — одна
константа модуля, расширяется без изменения контракта. Признак `creatable`
в `/types` и `/type` отражает это решение; `POST` к виду вне правила даёт
`403` с кодом `creation_not_allowed`. Ограничение закрывает служебные объекты
БСП (`Пользователи`, `КлючиДоступа`, `Файлы`, `ВерсииФайлов` и подобные):
их создание внешней системой не входит в замысел сервиса и не проверялось
приёмкой.

Стандартные реквизиты справочника: `Код` — при включённой автонумерации
назначает 1С (`writable=false`, возвращается сервисом отдельным полем), при
отключённой (`Autonumbering=false`) — записываем с проверкой длины
квалификатора, поскольку платформа сама код не генерирует;
`Наименование` — записываемо, если длина
по квалификатору больше нуля; `ПометкаУдаления`, `ЭтоГруппа` — только чтение;
`Родитель` — `writable=false`, причина «группы не поддерживаются»; `Владелец`
у подчинённого справочника — ссылка (см. ниже). Стандартные реквизиты документа:
`Дата` — записываема и обязательна (правило сервиса); `Номер` — `writable=false`
(назначает 1С), возвращается сервисом; `Проведен`, `ПометкаУдаления` — только
чтение, вне рамок сервиса. `required` прикладных полей — из проверки заполнения
метаданных; у табличной части — из её настройки; обязательность поля строки сама
по себе не означает обязательность строки.

`rules` поясняет: окончательное решение за штатной проверкой заполнения 1С
(условные правила из обработчиков схема не выводит); даты — ISO 8601 без зоны,
местное время базы; `null` — штатное пустое значение; документ создаётся
непроведённым; суммы и значения по умолчанию сервис не рассчитывает.

## Группы и подчинённые справочники

Иерархия групп и элементов: поиск и чтение возвращают только элементы; создание
группы отклоняется `400` с понятным кодом; `GET /object` на идентификатор группы
— `404`, группа для внешней системы не объект. `Родитель` описан, но не
записываем — перенос между группами вне рамок.

Подчинённые справочники поддерживаются, когда их владелец — один справочник:
`Владелец` описывается как обычная ссылка и обязателен к передаче при создании,
если у метаданных стоит проверка заполнения. Владелец с составным типом или
ссылкой на документ помечает справочник недоступным для создания: `/type`
возвращает описание, `POST` даёт понятный отказ. Поиск и чтение подчинённых
работают на общих основаниях.

## Поиск

`GET /search` ищет по одному виду из `type`. Вид должен быть поддерживаемым;
доступ к нему определяется правами пользователя — «чужих» справочников
отдельного списка больше нет: разрешено всё читаемое. Параметр `q` — непустая
после обрезки внешних пробелов строка; для справочников ищется вхождение в
наименование, для документов — в номер. Символы шаблона поиска (`%`, `_`, `[`)
трактуются как обычные символы. `limit` — целое 1–100, по умолчанию 20.
Неверные параметры — `400`.

Запрос выполняется с `РАЗРЕШЕННЫЕ`, исключает помеченные и группы, выбирает не
более `limit + 1`, сортировка — наименование (номер) затем ссылка. Ответ:
`{"items":[{"id":"<uuid>","name":"<наименование или номер>"}],"hasMore":true|false}`.
`hasMore=true` означает: уточните строку или поднимите лимит; постраничной
выдачи нет. Поиск не проверяет, на что ссылается поле: выбор объекта — за
клиентом, ссылочную целостность проверит запись.

## Чтение

`GET /object?type=&id=` — по UUID в нижнем регистре. Объект не найден,
оказался группой или недоступен пользователю — единый `404` без раскрытия
причины. Успех: `{"id","type","kind","header","tables"}`; сервисные поля
справочника — `code`, документа — `number`, `date`, `posted`. `header` содержит
записываемые поля шапки, `tables` — записываемые табличные части, значения —
в форматах из таблицы значений. Поля с неподдерживаемыми типами опускаются
(их состав виден в `/type`); номер, дата, признаки читаются из сохранённого
объекта, а не из прошлого запроса.

## Создание

`POST /object`, тело: `{"type":"<Вид.Имя>","header":{…},"tables":{…}}`.
Вид должен быть поддерживаемым и разрешённым к созданию (см. «Разрешение
на создание»). `header` и `tables` обязательны (могут быть пустыми объектами);
имена полей и частей — технические из `/type`; неизвестные ключи и недоступные
для записи поля отклоняются. Порядок:

1. Полностью разобрать JSON, включая проверку отсутствия хвоста после значения.
2. Проверить структуру, поля и значения по описанию типа; подготовить значения
   с точными типами 1С. Ссылки проверить на существование и доступность.
3. Создать объект, перенести шапку и строки; автозаполнение и обработку
   заполнения не вызывать — сервис не подбирает значения за пользователя.
4. В транзакции очистить очередь сообщений, вызвать штатную `ПроверитьЗаполнение()`;
   при отказе откатить и вернуть ошибку.
5. Записать без проведения (справочник — обычной записью); у документа после
   записи проверить `Проведен = Ложь`.
6. Ответ подготовить до завершения транзакции; при исключении откатить её.

Успех `201`: для справочника `{"id","type","kind","code"}`, для документа
`{"id","type","kind","number","date","posted":false}`; дата — ISO 8601 без
зоны. Каждый успешный запрос создаёт новый объект: защиты от повторов нет,
повтор после потери ответа небезопасен. Запись с флагом обмена, обходящая
штатные обработчики, запрещена.

## Ошибки и журналирование

Форма ошибки единая:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Объект не прошёл проверку заполнения",
    "details": [{"path": "header.Организация", "message": "Текст проверки 1С"}]
  }
}
```

`path` — путь в запросе (`header.Поле`, `tables.Товары[0].Поле`); если штатное
сообщение не определяет поле достоверно — `null`, текст сохраняется без
угадывания. Возвращаются все сообщения штатной проверки.

| Статус | Причина |
| --- | --- |
| `400` | Неверный JSON или хвост, структура, параметры, неизвестное поле или тип, неподдерживаемое значение или ссылка, создание группы |
| `403` | Нет права на операцию над видом либо вид не разрешён к созданию правилом сервиса |
| `404` | Объект не найден, группа или недоступен |
| `415` | Неподдерживаемый тип тела запроса |
| `422` | Штатная проверка заполнения отказала; объект не записан |
| `500` | Неожиданное исключение 1С; транзакция создания отменена |

Методы и пути вне таблицы маршрутов, аутентификационные отказы — в ведении
платформы и публикации. Сбой клиенту — краткий текст без стека; подробное
представление — в журнал регистрации с именем события сервиса. Тело запроса и
аутентификация целиком не журналируются.

## Стенд и приёмка

База — та же, что у сервиса счетов: публикация `/bsp-demo2` на `InfoBase20`,
адрес и учётные данные — в игнорируемом `src/tests/.env`. Обновлённое
расширение загружается в базу по явной команде пользователя (правила
AGENTS.md: без завершения сеансов, без автоматического применения);
выгрузка расширения в `.cfe` — по завершении.

Файл `src/tests/objects.http` содержит по запросу на каждый маршрут: список
типов, описание типа, поиск справочника и документа, чтение, создание
справочника и документа, отказ по обязательному полю. Создание контрольных
объектов — намеренно запускаемый шаг. Приёмка на стенде:

- каждый маршрут внешним HTTP-клиентом; `/type` описывает поля по действующим
  метаданным, ограничения типов и ссылки выводятся автоматически;
- поиск по подстроке/номеру, лимит, `hasMore`, экранирование шаблонов;
- созданные запросами справочник и документ открываются в 1С: покупатель,
  товар и суммы на месте, документ непроведён (проверяет пользователь вручную);
- создание элемента справочника `Валюты` подтверждает список допуска вне
  `_Демо*`; попытка создать объект служебного вида (`Пользователи`) даёт
  `403 creation_not_allowed`;
- счёт на оплату покупателю создаётся через `POST /object` тем же контрактом;
- отказы: неверный JSON, неизвестный тип, неизвестное поле, неподдерживаемый
  тип значения, несуществующая ссылка, отсутствие обязательного реквизита и
  обязательного поля строки — клиентские ошибки, после отказа новых объектов нет
  (список в клиенте до и после сравнивает пользователь);
- неподдерживаемые поля не мешают чтению и описаны в `/type` с `reason`.

Доказательства — в игнорируемых логах; в отчёте отдельно: проверено
автоматически, показано в клиенте, не проверено. Тестовые данные не создаются
без согласования — контрольные примеры берут существующие (партнёр «Альфа»,
товар и организация демо-данных из `.env`).

## Что остаётся исполнителю

Разбиение обработчиков и вспомогательных функций, точки параметризации модулей
по `Вид.Имя`, внутренние структуры обхода метаданных справочников и документов,
текстовые формулировки кодов ошибок. Эти решения не меняют публичный контракт,
не обходят штатную проверку и не добавляют операций. После утверждения
спецификации составляется план реализации.
