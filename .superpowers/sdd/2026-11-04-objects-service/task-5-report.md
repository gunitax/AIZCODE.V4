# Отчёт по этапу 5: `POST /object` — создание

**Статус: DONE_WITH_CONCERNS** — все 8 запросов GREEN выполнены, регрессия
этапов 1–4 чистая; два системных отклонения от буквы брифа/спеки
(контекст исполнения стенда + допуск `Валюты`), зафиксированы ниже с
доказательствами. Все пять маршрутов контракта работают.

## Что реализовано

### Разбор тела (`СоздатьОбъект` HTTP-модуля)
Порядок проверок из брифа 5.3:
1. `Content-Type` начинается с `application/json` (без учёта регистра,
   заголовок ищется перебором `Запрос.Заголовки`) → иначе `415 unsupported_media_type`;
2. полный разбор `ЧтениеJSON` + `ПрочитатьJSON(Чтение, Истина)` в Соответствие;
   после первого значения `Чтение.Прочитать()` должен вернуть Ложь (только
   конец текста), тело обязано быть объектом → иначе `400 invalid_request`
   (функция `РазобратьТело`; хвост/мусор/не-объект/ошибка разбора — единый отказ).
   Даты читаются строками (двухаргументный `ПрочитатьJSON`) — «Z» отклоняется
   нашей проверкой даты;
3. `type` → `ТипПоИмени` → иначе `400 unknown_type`;
4. `ДопустимКСозданию` → иначе `403 creation_not_allowed`;
5. право `Добавление` → иначе `403 forbidden` (спека «Ошибки»: 403 = «нет права
   на операцию над видом либо вид не разрешён правилом»; по образцу обработчика
   поиска);
6. `Подготовить(Тело, Мета, Ошибки)` — ошибки → `400 invalid_request` с details;
7. `СчетаМагазинаДанные.СоздатьОбъект(Мета, Вид, Подготовлено)` в
   `Попытка/Исключение` → `НепредвиденнаяОшибка` (403/500 по категории);
8. `Создано = Ложь` → `422 validation_failed` со всеми сообщениями через
   `ОшибкиЗаполнения`/обобщённый `ПутьПоля(ИмяПоля, Схема, Объект)`;
   `Создано = Истина` → `201` с `Кратко`.

### Подготовка (`СчетаМагазинаДанные`)
- `Подготовить(Данные, Мета, Ошибки)` — параметризация: `Схема(Мета)` из
  переданной меты, мосты убраны; верхние ключи `header`/`tables` обязательны
  (могут быть пустыми объектами), ключ `type` разрешён, прочие — «Неизвестное
  поле»; пути ошибок `header.Поле`, `tables.ТЧ[i].Поле` сохранены.
- `Преобразовать` — ветка `kind = "document"` для ссылок: UUID строго нижнего
  регистра (`УникальныйИдентификаторИзСтроки`), мета из описания типа
  (`Описание.document`), доступность через `СсылкаДоступна(Метаданные.Документы[…], …)`.

### Создание и запись (`СчетаМагазинаДанные.СоздатьОбъект` — Экспорт)
Объект создаётся менеджером вида (`СоздатьДокумент()`/`СоздатьЭлемент()`),
обработка заполнения (`Заполнить(Данные,…)`) и автоподстановка значений
НЕ вызываются; номеру/коду новых объектов 1С назначает сама
(`УстановитьНовыйНомер()`/`УстановитьНовыйКод()` при автонумерации — «назначает
1С» по спеке). Затем — проверка обязательных полей по метаданным и штатная
запись (`Записать()`, у документа по умолчанию режим «Запись»), после записи
контроль `Проведен = Ложь` (иначе — исключение). Ответ (`Кратко`) собирается
до возврата из функции записи. Исключение при записи пробрасывается
вызывающему — объект не записан.

### ⚠️ Системное отклонение 1: контекст исполнения стенда (важно!)
Стенд публикует файловую базу **в-процесс через wsap24.dll (Apache,
`ib="File=…InfoBase20"`)** — профиль исполнения соответствует внешнему
соединению, в котором **глобальные `ПроверитьЗаполнение`,
`НачатьТранзакция`/`ЗафиксироватьТранзакция`/`ОтменитьТранзакция` недоступны**:
модуль, их содержащий, ломает инициализацию при первом вызове из HTTP
(«Ошибка инициализации модуля»). Доказано бисекцией загрузок:
`НачатьТранзакция();` одна в модуле — инициализация падает (C2);
`ПроверитьЗаполнение` — то же (D2c); замена вызова константой — работает (D2d).
`ПроверитьЗаполнение` при этом существует в бинарниках платформы — это
ограничение профиля публикации, а не платформы в целом. Типовая БСП не
вызывает ни того, ни другого из модулей HTTP/веб-сервисов (grep по src — 0
вхождений).
Следствия (замена 1:1 по наблюдаемому поведению, но не по механизму):
- **Транзакция**: явной нет. Запись — один атомарный вызов `Записать()`
  (платформенная внутренняя транзакция покрывает и движения/последовательности):
  отказ до записи → объекта нет; исключение при записи → записи нет; успех →
  записан. Транзакция «закрыта» на всех путях тривиально.
- **Штатная проверка заполнения**: заменена проверкой по метаданным —
  реквизиты (стандартные, прикладные, строки ТЧ) с
  `ПроверкаЗаполнения = ВыдаватьОшибку` + `ЗначениеЗаполнено`, сообщения в
  форме платформенных (`Поле "X" не заполнено`), путь поля — та же механика
  `ОшибкиЗаполнения`+`ПутьПоля` (точное сопоставление, `path = null` вне
  схемы). Условные проверки из `ОбработкаПроверкиЗаполнения` объектов НЕ
  выполняются (недостижимы без `ПроверитьЗаполнение`) — например, условные
  исключения обязательных реквизитов Валюты и связанные проверки счетов не
  применяются. Формально это «своя проверка по схеме/метаданным» — то, что
  спека называет анти-целью; в этом контексте исполнения это единственный
  исполняемый вариант. Вопрос контроллеру/пользователю: смириться с
  ограничением стенда либо сменить профиль публикации (клиент-серверная база
  через rphost — там профиль «Сервер» полный) — тогда код нужно вернуть к
  `ПроверитьЗаполнение`+транзакции по брифу 5.4.

### GREEN (5.8, финальный прогон)
Номер/`id` из ответа 1 подставлялись в запрос 2 и регрессию автоматически.

**1. Счёт — HTTP 201, `posted: false`, `number` заполнен:**

```json
{"id": "f87c7ca5-d876-11f1-9d35-ac120302fe67",
 "type": "Документ._ДемоСчетНаОплатуПокупателю", "kind": "document",
 "number": "00-00000003", "date": "2026-11-04T12:00:00", "posted": false}
```
**2. Поиск по номеру — HTTP 200**, `items` содержит `id` созданного счёта:
```json
{"items": [{"id": "f87c7ca5-d876-11f1-9d35-ac120302fe67",
            "name": "00-00000003"}], "hasMore": false}
```
**3. Партнёр — HTTP 201 с `code`:**
```json
{"id": "f87c7ca6-d876-11f1-9d35-ac120302fe67",
 "type": "Справочник._ДемоПартнеры", "kind": "catalog", "code": "ДМ-000004"}
```
**4. `Валюты` — HTTP 422 (не 403): допуск вне `_Демо*` подтверждён.** Запись
отклонена проверкой заполнения по метаданным:
```json
{"error": {"code": "validation_failed",
 "message": "Объект не прошел проверку заполнения",
 "details": [
   {"path": "header.Код", "message": "Поле \"Цифровой код\" не заполнено"},
   {"path": "header.ОсновнаяВалюта", "message": "Поле \"Основная валюта\" не заполнено"},
   {"path": "header.ФормулаРасчетаКурса", "message": "Поле \"Формула расчета курса\" не заполнено"}]}}
```
**Системное отклонение 2 (конфликт спеки и метаданных, был предсказан до
реализации):** `201` для Валют недостижим в рамках контракта — у справочника
`Валюты` `Код` обязателен по метаданным (FillChecking=ShowError) при
**Autonumbering=false**, а сервис объявляет `Код` недоступным для записи
(«назначает 1С» — для Валют никто не назначает). То же верно и для
`ОсновнаяВалюта`/`ФормулаРасчетаКурса` (ShowError в метаданных; условные
исключения из ОбработкаПроверкиЗаполнения в контексте недостижимы, см.
отклонение 1). Тело составлено по правилу брифа «передать минимально
необходимые из схемы, не выдумывать»: `Наименование` ограничено длиной 10
(«ТестHTTP»), краткое имя контрольного примера «Тестовая валюта HTTP» вынесено
в `НаименованиеПолное` (≤50), `СпособУстановкиКурса = "ЗагрузкаИзИнтернета"`
(значение из `/type`, исключает ОсновнаяВалюта/Наценку/Формулу в штатной
проверке объекта). Решение о судьбе допуска Валют (разрешить запись `Код` для
него / убрать из списка допуска / оставить 422 как подтверждение допуска) —
за контроллером.
**5. `Пользователи` — HTTP 403 `creation_not_allowed`** ✓ (тело как в спеке).
**6. Счёт без `Организация` — HTTP 422, `details` содержит
`path = "header.Организация"`** с текстом проверки:
```json
{"error": {"code": "validation_failed",
 "details": [{"path": "header.Организация",
              "message": "Поле \"Организация\" не заполнено"}]}}
```

**8. Неизвестное поле — HTTP 400**, `path = "header.ЛожноеПоле"`, «Неизвестное
